# git-rebase (2026-11-02)

`git rebase` replays your commits on top of another base, producing a linear history instead of a merge commit.

## Common uses

- **Update a feature branch:** `git rebase main` moves your work onto the latest main.
- **Clean up commits:** `git rebase -i HEAD~4` lets you squash, reword, reorder, or drop commits before review.
- **Transplant a branch:** `git rebase --onto new-base old-base feature` moves a range of commits elsewhere.

## Handling conflicts

Resolve the files, run `git add`, then `git rebase --continue`. If things go sideways, `git rebase --abort` returns you to where you started.

## Rules of thumb

1. Never rebase commits that others have already pulled; rebasing rewrites history and changes commit hashes.
2. After rebasing a pushed branch, use `git push --force-with-lease` rather than `--force`, so you don't overwrite a teammate's work.
3. Commit or stash changes first, so the working tree is clean.
4. Remember `git reflog` can recover commits after a mistaken rebase.

Rebase for tidy, readable history; merge when preserving the exact record matters.
