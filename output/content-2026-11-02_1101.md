# GitHub Actions Caching Tips

**Date:** 2026-11-02

Based on the GitHub Docs dependency caching reference and the `actions/cache` repository, both visited in a browser during research.

## 1. Key the cache on your lockfile
Use `hashFiles()` in the key so the cache refreshes only when dependencies change:
```yaml
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: npm-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      npm-${{ runner.os }}-
```
Source: [Dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)

## 2. Add `restore-keys` for partial hits
If there is no exact match, `restore-keys` falls back to prefix matches. A near-miss cache is usually faster than a cold start.

## 3. Know the search order
The action searches the current branch first (exact key, then restore-key prefixes). If nothing matches, it retries on the default branch. Scope restrictions apply during the search.

## 4. Watch size and eviction
- Entries not accessed for over 7 days are removed.
- The default limit is 10 GB per repository. Beyond that, GitHub saves new caches and evicts old ones until the total is under the limit.
- Eviction can cause cache thrashing (caches created and deleted at a high rate). Remove caching from workflows that don't benefit, or raise the limit in Actions settings.
- Rate limits: 200 uploads/min and 1500 downloads/min per repository.

## 5. Never cache secrets
Anyone with read access can open a pull request and read cache contents, and forks can access caches on the base branch. Don't store tokens or credentials in cache paths.

## 6. Prefer setup actions' built-in caching
Many `setup-*` actions offer a `cache:` option. The `actions/cache` README covers the underlying action.
Source: [actions/cache](https://github.com/actions/cache)
