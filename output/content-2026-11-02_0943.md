# GitHub Actions Security Best Practices

**Date:** 2026-11-02

Summary of guidance from GitHub Docs and GitHub Security Lab, based on pages visited in a browser during research.

## 1. Apply least privilege to secrets and tokens
Anyone with write access to a repository can read all of its secrets, so credentials used in workflows should have only the privileges they need. Restrict the `GITHUB_TOKEN` with an explicit `permissions:` block.
Source: [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)

## 2. Treat untrusted input as hostile (script injection)
For inline scripts, the preferred approach is to put the expression value into an intermediate environment variable instead of interpolating `${{ }}` directly into the shell script. Where possible, use an action instead of an inline script.
Source: [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)

## 3. Avoid "pwn requests"
Using `pull_request_target` together with an explicit checkout of an untrusted PR is dangerous and can lead to repository compromise. These workflows are privileged: they can have write access and share the main branch cache. GitHub Security Lab describes the safer pattern. Build untrusted code in an unprivileged `pull_request` workflow, then handle results in a separate `workflow_run` workflow. Artifacts from untrusted PRs remain untrusted.
Sources: [Preventing pwn requests (Security Lab)](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/), [Securely using pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)

## 4. Be careful with third-party actions and keep them updated
Jobs in a workflow can interact with and compromise other jobs, so vet third-party actions and reusable workflows. The docs recommend Dependabot version updates, CODEOWNERS for workflow files, code scanning, and OpenSSF Scorecards.
Source: [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)

## 5. Use OIDC instead of long-lived cloud credentials
OpenID Connect lets workflows authenticate to cloud providers without stored long-lived secrets.
Source: [OIDC reference](https://docs.github.com/en/actions/reference/security/oidc)

## 6. Harden runners
Use just-in-time runners for self-hosted setups, and review the supply chain of GitHub-hosted runners.
